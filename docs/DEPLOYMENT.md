# Deployment — MnM Tickets

## Development setup (local)

### Prerequisites

- Node.js >= 24 (the build machine has Node 24.19.0; verify with `node --version`).
- Git (for version control and migration tracking).
- ~460 MB free disk space (SQLite DB, node_modules, dist output).
- No PostgreSQL or Docker required — the lean stack uses SQLite in development.

### 1. Environment configuration

Copy `.env.example` to `.env` and fill in the values:

```bash
cp .env.example .env
```

Edit `.env` with your settings:

| Variable | Required? | Default / example | Description |
|---|---|---|---|
| `PORT` | no | `8787` | Server bind port. |
| `BIND_HOST` | no | `127.0.0.1` | Interface to bind to. |
| `PUBLIC_ORIGINS` | yes (for production) | `http://localhost:8787` | Comma-separated origins allowed for state-changing requests (CSRF/origin check). Must be the public site origin in production. |
| `APP_SECRET_KEY` | yes | generated by `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` | Master secret for session tokens, guest-order links and QR integrity. Rotate if ever exposed. |
| `NODE_ENV` | yes | `development` | Must be `production` for any public deployment. |
| `DATABASE_FILE` | yes (dev) | `data/mnm-dev.sqlite` | Local SQLite file path. Gitignored. |
| `PAYMENT_PROVIDER` | no | `dev` | `dev` | `daraja`. Set to `daraja` only when live M-Pesa credentials are configured. |
| `PAYMENT_DEV_FORCE_STATUS` | no | (empty) | Optionally force: `success` or `failure` for the dev adapter (testing purposes only). |
| `MPESA_ENV` | no (daraja mode) | `sandbox` | `sandbox` | `production`. |
| `MPESA_SHORTCODE` | no (daraja mode) | — | Paybill/Till number for STK push. |
| `MPESA_CONSUMER_KEY` | no (daraja mode) | — | OAuth consumer key from Safaricom. |
| `MPESA_CONSUMER_SECRET` | no (daraja mode) | — | OAuth consumer secret from Safaricom. |
| `MPESA_CALLBACK_BASE` | no (daraja mode) | — | Public HTTPS URL where Daraja POSTs callbacks. Must be a reachable host. |
| `MPESA_PASSKEY` | no (daraja mode) | — | Daraja API passkey for the shortcode. |
| `EMAIL_PROVIDER` | no | `console` | `console` | `smtp`. Set to `smtp` and fill SMTP_URL/SMS_* for real email/SMS. |
| `SMS_PROVIDER` | no | `console` | `console` | `africastalking` etc. |
| `SMTP_URL` | no (console mode) | — | If EMAIL_PROVIDER=smtp, the SMTP connection URL. |
| `SMS_API_BASE` | no (console mode) | — | If SMS_PROVIDER≠console, the API base URL. |
| `SMS_API_KEY` | no (console mode) | — | If SMS_PROVIDER≠console, the API key. |
| `NOTIFY_FROM` | no (console mode) | `info@example.com` | Sender address for email notifications. |

### 2. Database initialisation

The app uses SQLite with versioned migrations. On first run:

```bash
# Apply pending migrations (creates data/mnm-dev.sqlite if missing)
npm run migrate
```

This applies `db/migrations/0001_init.sql` then `0002_scan_log_unknown.sql` in filename order, inside a transaction.

To seed development data (staff logins, sample events, pricing terms):

```bash
npm run seed
```

This guards against running with `NODE_ENV=production` — it will abort with a clear message if the env says production.

### 3. Running the development server

```bash
npm run dev
```

The server starts at `http://127.0.0.1:8787` (configurable via `PORT` and `BIND_HOST` in `.env`).

### 4. Running tests

```bash
npm test
```

Runs the full test suite (unit, integration, HTTP). All 36 tests should pass (29 + 7 HTTP integration).

```bash
# Run a single test file
npx tsx --test tests/orders.test.ts
```

### 5. Production build

```bash
npm run build
```

Compiles TypeScript to `dist/` and verifies no errors. The production build is the artifact that gets deployed to a Cloudflare Workers environment or any Node.js-compatible hosting.

### 6. Running in production mode

```bash
NODE_ENV=npm run start
```

or

```bash
npm start
```

The `start` script runs `node --import tsx src/server.ts`, which starts the Hono server with production headers.

## Production deployment

### Target environment

The application is designed for Cloudflare Workers runtime (the `hono` stack is ~40 kB, zero-dep). However, it can run on any Node.js >= 24 environment with the Hono node-server adapter.

### Build artifact

The `npm run build` command produces:

- `dist/src/**` — compiled ES modules.
- `dist/tsconfig.json` — resolved type config.
- Source maps (optional, for debugging).

No compiled assets are copied from a separate build step — the Hono app renders JSX server-side and serves minimal static assets (favicon, CSS design system) from the `src/views/` directory.

### Deployment steps

1. Ensure `NODE_ENV=production` in your environment.
2. Set `PUBLIC_ORIGINS` to your production site origin (e.g. `https://mnm-tickets.example.com`).
3. If using M-Pesa Daraja live:
   - Add `MPESA_ENV=production`
   - Add `MPESA_SHORTCODE`, `MPESA_CONSUMER_KEY`, `MPESA_CONSUMER_SECRET`, `MPESA_PASSKEY`
   - Set `MPESA_CALLBACK_BASE` to your production HTTPS callback URL (must be reachable by Safaricom's network).
   - Set `PAYMENT_PROVIDER=daraja`
4. If using dev simulator only (no live M-Pesa):
   - Keep `PAYMENT_PROVIDER=dev`
   - Leave MPESA vars empty — they are ignored when provider is `dev`.
5. Apply migrations on the production database:
   ```bash
   DATABASE_FILE=path/to/production.sqlite npm run migrate
   ```
6. Seed only if needed (the seed script aborts with `NODE_ENV=production`):
   - For initial setup, you can manually run the migration SQL or insert seed data via a one-off script.
7. Start the server:
   ```bash
   npm run start
   ```
8. Verify:
   - Health check: `GET /` renders the home page.
   - Auth: `POST /staff/login` with valid credentials sets a session cookie.
   - Ticket flow: create event → add category → checkout → dev sim callback → verify ticket → scan.

### Environment variable notes

- `.env` is gitignored and must never be committed with real values.
- `APP_SECRET_KEY` must be a 32-byte random hex string. Regenerate if the secret is ever exposed.
- `PUBLIC_ORIGINS` is a comma-separated list. In development, include `http://localhost:8787`. In production, replace with your actual site origin.
- Payment-related env vars are only read when `PAYMENT_PROVIDER=daraja`. When `PAYMENT_PROVIDER=dev`, they are ignored.

### Health checks

The app has no explicit `/health` endpoint, but the following routes can be used to verify basic functionality after deployment:

- `GET /` — home page (renders only on-sale events).
- `GET /events` — lists published events.
- `POST /staff/login` — authenticates and sets session cookie.
- `GET /order/<ref>?t=<token>` — shows order status page.

### Rollback procedure

If a deployment causes issues:

1. The SQLite database is file-based — restore a previous `.sqlite` backup.
2. The `dist/` directory is generated from source — redeploy the previous `npm run build` output.
3. Environment variables can be reverted by updating `.env` and restarting the server.
4. No database schema changes are irreversible without an explicit migration — new migrations are appended in filename order; old ones are never deleted.

### DNS and domain considerations

- The application does not embed any hardcoded domain names. All origins are read from `PUBLIC_ORIGINS` env var.
- Callbacks (M-Pesa, email, SMS) use URLs configured at runtime. Ensure your DNS and TLS certificate cover any custom callback hosts.

### Credentials and secrets

- Never commit `.env` or any file containing real credentials.
- `APP_SECRET_KEY` is the only secret required for basic operation; rotate if exposed.
- M-Pesa credentials are read from env at startup; they are not stored in code or logs.
- If deploying to a platform that injects env vars (e.g. Cloudflare Workers, Fly.io, Render), set the variables in the platform's dashboard, not in the codebase.

### Development-to-production checklist

- [ ] `NODE_ENV=production`
- [ ] `PUBLIC_ORIGINS` set to production origin
- [ ] `APP_SECRET_KEY` set (32-byte random hex)
- [ ] Database migrations applied to production SQLite/PostgreSQL
- [ ] M-Pesa: either `PAYMENT_PROVIDER=dev` (simulator) or full Daraja creds + callback URL
- [ ] Email/SMS providers configured (or left as `console` dev adapter)
- [ ] `npm run build` succeeds with no errors
- [ ] Full test suite passes (`npm test`)
- [ ] Manual flow test: event create → checkout → payment → ticket verify → scan
- [ ] Security review: headers, CSRF origin checks, rate limiting
- [ ] Documentation reviewed (this file + all docs/)
